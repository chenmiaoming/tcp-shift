# gVisor upstream policy

`tcp-shift` treats gVisor Netstack as an upstream dependency, not as vendored source.
For external Go users, gVisor explicitly maintains a synthetic `go` branch that contains
rendered/generated sources and is compatible with standard Go tooling. The authoritative
development tree remains `master`, and gVisor's automation reflects it into `go`.

Therefore tcp-shift follows **`google/gvisor@go`**, not a raw checkout of `master`.
The project has two dependency tracks with different purposes.

## 1. Verified synthetic-Go baseline

`.gvisor-baseline` contains the exact commit from gVisor's synthetic `go` branch used
for normal development, benchmarks, and release candidates. A baseline is reproducible
and must have passed:

- tcp-shift build and CLI smoke tests;
- native Linux CUBIC/BBR and gVisor CUBIC/tcp-shift-BBR long-fat-network comparisons;
- CPU, RSS, throughput, and recovery reporting;
- protocol correctness tests added as the project matures.

Changing the baseline is an explicit dependency update, not an incidental side effect
of building tcp-shift.

## 2. Moving upstream compatibility track

CI also builds with `GVISOR_REF=go`. This resolves the current protected synthetic
`go` branch to a concrete commit, applies tcp-shift's narrow TCP integration patch,
builds the relay, and records the resolved SHA.

This job is intentionally strict. If a reflected gVisor update changes an internal TCP
interface that our patch depends on, CI should fail immediately. The failure is a
compatibility signal; it must not silently fall back to an older revision.

Once the moving-`go` job and the benchmark/correctness suite are green, that synthetic
Go SHA can be promoted into `.gvisor-baseline`.

## Relationship to gVisor master

gVisor's `master` tree is Bazel-first. It contains source templates such as
`*.tmpl.go` and `*.tmpl.s` that are rendered from Go runtime facts by gVisor's build
rules. A standard external `go build` must not consume that raw tree directly.

The protected synthetic `go` branch is generated by gVisor automation from `master`.
For example, the 2026-08-21 synthetic commit used while establishing this policy was
created by `gVisor bot` with a merge message referring to master revision `80336ad54`.
This is the upstream-supported bridge we rely on instead of reimplementing gVisor's
Bazel generators.

## Why releases are not built from a floating branch

A production binary must be reproducible. Building a release from a moving `go` branch
would make two builds with the same tcp-shift source potentially contain different
network stacks. Therefore:

- compatibility CI follows moving `google/gvisor@go`;
- release artifacts use a verified exact synthetic-Go SHA;
- every binary embeds both the requested gVisor ref and the resolved gVisor SHA.

This provides continuous compatibility without sacrificing reproducibility.

## Patch-surface rule

The long-term goal is to keep tcp-shift-specific changes to gVisor TCP as small and
mechanical as possible. The preferred order is:

1. use public Netstack APIs directly;
2. add generic congestion-control/pacing extension points that could plausibly be
   accepted upstream;
3. keep tcp-shift BBR implementation in a separate added source file;
4. avoid replacing large upstream functions or copying unrelated gVisor code.

The original PoC replaced `sender.sendData()` wholesale. The current patcher no longer
does that: it preserves the upstream function and inserts pacing initialization,
admission, and accounting at three narrow anchors, plus the required timer/state hooks.
This substantially reduces rebase surface, but it still patches private TCP internals.
Before a production release, the preferred end state is a small generic hook design
that can be proposed upstream.

## Updating gVisor locally

Build the verified baseline:

```bash
bash ./scripts/build.sh
./bin/tcp-shift --version
```

Build current external-Go upstream:

```bash
GVISOR_REF=go bash ./scripts/build.sh
./bin/tcp-shift --version
```

Test a specific commit from the synthetic `go` history:

```bash
GVISOR_REF=<synthetic-go-commit> bash ./scripts/build.sh
```

The build rejects raw Bazel revisions containing `*.tmpl.*` files with a diagnostic
rather than failing later in the Go assembler.

If compatibility and benchmark results are acceptable, update `.gvisor-baseline` in
a dedicated dependency-update commit or pull request.

## Promotion criteria

A future automated baseline-promotion workflow may propose updates, but it should not
auto-merge them. At minimum promotion should require:

- build compatibility;
- TCP relay integration tests;
- repeated long-fat-network benchmark results against native Linux CUBIC and BBR;
- no material protocol-correctness or loss-recovery regression;
- no material throughput, CPU, or RSS regression relative to the current baseline;
- review of relevant gVisor TCP changes reflected between the old and new synthetic
  revisions.

A constrained-memory profile may be added later as a separate deployment target. It is
not part of the current upstream-promotion gate, whose first priority is a stable,
production-grade transport implementation.
